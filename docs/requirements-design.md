## 2. 产品定位与目标

### 2.1 一句话定位

**Follow Me 是一个轻量级的位置共享与汇合（rendezvous）工具，帮助一小群人在大型活动、户外徒步、商场、展会等场景中实时看到彼此的位置，并快速找到对方。**

### 2.2 解决的核心痛点

在演唱会、音乐节、马拉松、登山、漫展、大型展会等人流密集的场所，朋友之间很容易走散。现有方案存在明显短板：

| 现有方案 | 短板 |
| --- | --- |
| 微信实时位置共享 | 一次只能看少数人、时长有限、界面简陋、无法长时间后台运行 |
| 专业对讲机 | 需要额外硬件，普通用户嫌麻烦 |
| 地图 App 的位置共享 | 偏向导航，不适合"一群人互相找"的场景 |

Follow Me 聚焦「**小群体临时汇合**」这一具体痛点，主打**轻量、实时、隐私可控**。

### 2.3 产品目标

| 目标 | 衡量方式 |
| --- | --- |
| 降低使用门槛 | 扫码即可加入小队，无需复杂注册 |
| 实时看到彼此 | 成员位置在地图上秒级更新 |
| 快速找到对方 | 提供「箭头 + 距离」指南针式指引 |
| 隐私可控 | 活动结束位置数据自动清除，可随时暂停共享 |

### 2.4 非目标（MVP 阶段不做）

- 不做**陌生人社交**
- 不做**长期好友关系链**
- 不做**精细导航**（转向提示等），只做方向指引

## 3. 术语与约定

| 术语 | 含义 |
| --- | --- |
| 小队（Squad / Group） | 一次临时创建的成员集合，用于本次汇合 |
| 队长（Owner） | 创建小队的人，拥有解散小队等权限 |
| 成员（Member） | 加入小队的人 |
| 邀请码 / 二维码 | 加入小队的凭证 |
| 位置共享（Sharing） | 成员将自身实时位置上报给小队的行为 |
| 指南针导航（Compass） | 选定某成员后，以箭头 + 距离指向对方的指引 |
| 汇合（Rendezvous） | 成员之间找到彼此并会合的过程 |

## 4. 目标用户与场景

### 4.1 目标用户画像

- 参加大型活动（演唱会、音乐节、展会、漫展）的**朋友群体**
- 户外徒步、骑行、越野的**小队**
- 家长带小孩、老人出行的**家庭**
- 旅游团、研学团的**临时组织者**

共同特征：临时性强、群体规模小（数人到数十人）、对隐私敏感、希望"开箱即用"。

### 4.2 核心场景

**场景 A：演唱会走散（主场景）**
小李和 4 个朋友去看演唱会，散场时人潮汹涌走散。小李打开 App，大家本就在同一小队，地图上能看到彼此位置；小李选中朋友小王，按箭头方向走，距离逐渐缩短直至会合。

**场景 B：户外徒步小队**
10 人徒步队伍拉得很长，队长想随时掌握队员位置，确认没人掉队。

**场景 C：家庭出游**
家长带孩子和老人逛大型商场/展会，临时分头行动，需要随时看到家人位置并快速汇合。

### 4.3 用户旅程（场景 A）

```
队长                          成员
 │                            │
 ├─ 1. 创建小队 → 生成二维码    │
 │                            │
 │◀──── 2. 扫码加入 ──────────┤
 │                            │
 ├─ 3. 双方开启位置共享         ├─ 3. 开启位置共享
 │                            │
 ├─ 4. 地图上看到彼此           ├─ 4. 地图上看到彼此
 │                            │
 ├─ 5. 选中对方 → 箭头指引       │
 ├─ 6. 按方向走，距离缩短 → 会合  │
 │                            │
 └─ 7. 活动结束 → 解散小队 → 数据清除
```

## 5. 整体方案设计

### 5.1 系统架构

```
┌──────────────────────────────────────────────┐
│                  移动客户端                      │
│  地图渲染 │ 定位采集 │ 指南针指引 │ 小队管理 UI    │
├──────────────────────────────────────────────┤
│                  实时通信层                      │
│        WebSocket / MQTT（位置上报与下发）         │
├──────────────────────────────────────────────┤
│                  后端服务层                      │
│  小队服务 │ 位置网关 │ 推送服务 │ 鉴权服务         │
├──────────────────────────────────────────────┤
│                  存储层                         │
│  会话/位置（内存/Redis，短时效）│ 元数据（DB）      │
└──────────────────────────────────────────────┘
        外部依赖：地图 SDK（高德/Mapbox） + 定位
```

### 5.2 设计原则

- **轻量优先**：加入与使用路径尽可能短（扫码即用）。
- **实时优先**：位置链路低延迟，地图秒级更新。
- **隐私优先**：位置数据"短时效、用完即删"，最小化采集与留存。
- **可演进**：MVP 聚焦核心四功能，扩展能力（轨迹回放等）后置。

### 5.3 客户端核心模块

| 模块 | 职责 |
| --- | --- |
| 小队管理 | 创建/加入/退出/解散小队，二维码生成与扫描 |
| 定位采集 | 获取设备 GPS/网络定位，按策略上报 |
| 地图展示 | 渲染成员位置与朝向 |
| 指南针导航 | 计算对目标成员的方位角与距离，渲染箭头 |
| 隐私控制 | 暂停/恢复共享，数据清除 |

## 6. 功能需求详述

### 6.1 创建 / 加入小队

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-SQ-01 | 用户可创建临时小队，系统生成邀请码与二维码 | M |
| F-SQ-02 | 用户扫码或输入邀请码即可加入小队，无需复杂注册（支持游客/昵称模式） | M |
| F-SQ-03 | 成员可主动退出小队 | M |
| F-SQ-04 | 队长可解散小队 | M |
| F-SQ-05 | 显示小队成员列表与在线状态 | M |
| F-SQ-06 | 邀请码/二维码可设置有效期，过期后失效 | S |
| F-SQ-07 | 小队人数上限（基础版限额，见盈利模式） | S |

### 6.2 实时位置共享

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-LOC-01 | 成员位置在地图上实时显示，含移动方向（朝向） | M |
| F-LOC-02 | 位置数据秒级更新（目标 ≤ 3s 端到端延迟） | M |
| F-LOC-03 | 支持后台持续共享（应用切到后台仍可上报，受系统策略约束） | M |
| F-LOC-04 | 上报频率可根据移动状态/电量自适应（静止降频、移动升频） | S |
| F-LOC-05 | 弱网/断线自动重连并补发最新位置 | S |
| F-LOC-06 | 标识成员位置精度（如 GPS 弱时给出提示） | S |

### 6.3 指南针 / 箭头导航

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-NAV-01 | 选定某成员后，提供「箭头 + 距离」的方向指引 | M |
| F-NAV-02 | 箭头随自身朝向（设备方向传感器）实时旋转，指向目标 | M |
| F-NAV-03 | 实时显示到目标成员的直线距离 | M |
| F-NAV-04 | 距离接近阈值时给出"即将会合"提示 | S |
| F-NAV-05 | 明确不提供转向级精细导航（非目标） | W |

### 6.4 临时性与隐私

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PRI-01 | 小队解散或活动结束后，位置数据自动清除 | M |
| F-PRI-02 | 用户可随时暂停 / 恢复位置共享 | M |
| F-PRI-03 | 暂停共享时，其他成员看不到该用户实时位置（显示为"已暂停"） | M |
| F-PRI-04 | 位置历史默认不留存（轨迹回放为付费高级功能，见 §15） | M |
| F-PRI-05 | 首次使用明确告知定位权限用途，获取用户同意 | M |

## 7. 关键交互流程

### 7.1 创建并加入小队

```
队长 → App: 点击「创建小队」
App → 后端: 创建小队请求
后端 → App: 返回 squadId + 邀请码 + 二维码
队长 → 成员: 出示二维码 / 分享邀请码
成员 → App: 扫码/输码加入
App → 后端: 加入小队请求（昵称）
后端 → 小队: 广播「新成员加入」
App(全员): 刷新成员列表
```

### 7.2 实时位置上报与下发

```
成员 App → 位置网关(WS): 周期上报 {squadId, userId, lat, lng, heading, ts}
位置网关 → Redis: 写入最新位置（带 TTL）
位置网关 → 小队其他成员: 实时下发位置更新
其他成员 App: 更新地图标记 + 重算指南针箭头
```

### 7.3 指南针导航

```
用户 → App: 在成员列表选中目标
App: 监听设备方向传感器（heading）
App: 计算 自身坐标 → 目标坐标 的方位角 bearing
App: 箭头旋转角 = bearing - heading
App: 展示箭头 + 直线距离（随双方移动持续刷新）
距离 < 阈值 → 提示「即将会合」
```

### 7.4 解散与数据清除

```
队长 → App: 解散小队（或活动结束触发）
App → 后端: 解散请求
后端: 删除小队会话 + 清除全部成员位置数据
后端 → 全员: 广播「小队已解散」
App: 退出小队界面
```

## 8. 数据模型设计

> 原则：位置等敏感数据**短时效存储**（内存/Redis + TTL），元数据最小化。

### 8.1 小队（Squad）

```json
{
  "squad_id": "SQ-8FK3D",
  "owner_id": "u_001",
  "name": "演唱会小队",
  "invite_code": "8FK3D",
  "invite_expire_at": "2026-05-31T23:59:59Z",
  "status": "active",          // active | dissolved
  "created_at": "2026-05-31T18:00:00Z",
  "member_limit": 10
}
```

### 8.2 成员（Member）

```json
{
  "user_id": "u_002",
  "squad_id": "SQ-8FK3D",
  "nickname": "小王",
  "sharing": true,             // 是否正在共享位置
  "online": true,
  "joined_at": "2026-05-31T18:02:00Z"
}
```

### 8.3 位置（Location，短时效，TTL）

```json
{
  "squad_id": "SQ-8FK3D",
  "user_id": "u_002",
  "lat": 31.2304,
  "lng": 121.4737,
  "heading": 187.5,            // 朝向（度）
  "accuracy": 12.0,            // 精度（米）
  "ts": "2026-05-31T18:05:30Z"
}
```

> 位置数据建议存于内存/Redis 并设置 TTL；小队解散即整体清除（满足 F-PRI-01 / F-PRI-04）。

## 9. 隐私与安全设计

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| SEC-01 | 位置数据传输全程加密（TLS / WSS） | M |
| SEC-02 | 位置数据短时效存储，小队解散即清除，不做长期留存 | M |
| SEC-03 | 加入小队需有效邀请凭证，非成员无法获取小队位置 | M |
| SEC-04 | 用户可随时暂停共享，暂停后立即停止上报与下发 | M |
| SEC-05 | 定位权限申请遵循最小必要、明示用途、用户同意原则 | M |
| SEC-06 | 遵循适用的隐私合规要求（如个人信息保护相关法规），提供隐私政策 | M |
| SEC-07 | 防止位置数据被同小队外的人越权访问（鉴权 + 小队隔离） | M |

## 10. 非功能需求

| 类别 | 需求 |
| --- | --- |
| **易用性** | 加入路径 ≤ 2 步（扫码 → 进入）；首屏即见地图与成员 |
| **实时性** | 位置端到端延迟目标 ≤ 3 秒 |
| **可靠性** | 弱网自动重连，位置补发；服务端高可用 |
| **续航/性能** | 定位上报自适应频率，控制耗电；地图渲染流畅（≥ 30fps） |
| **可扩展性** | 实时通信层支持横向扩容以应对高并发位置同步 |
| **兼容性** | 覆盖主流 iOS / Android 版本；适配主流机型分辨率 |
| **成本可控** | 高并发位置同步的服务器成本可控（见 §12） |

## 11. 技术选型建议

| 维度 | 建议 | 理由 |
| --- | --- | --- |
| 客户端 | iOS / Android 原生，或 Flutter / React Native 跨端 | 需要定位、方向传感器、后台运行，原生能力更可控 |
| 地图 SDK | 高德 / 百度（国内）或 Mapbox / Google Maps（海外） | 成熟地图与定位能力 |
| 实时通信 | WebSocket 或 MQTT | 低延迟双向通信，MQTT 适合海量轻量消息 |
| 位置存储 | Redis（带 TTL） | 短时效、高吞吐，契合"用完即删" |
| 元数据存储 | PostgreSQL / MySQL | 小队、成员等结构化元数据 |
| 后端 | Go / Node.js | 高并发实时连接处理能力强 |
| 推送 | APNs / FCM | 后台/离线提醒 |

## 12. 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 室内定位精度差 | GPS 在室内/地下表现差 | 融合网络/Wi-Fi/蓝牙定位；展示精度并提示；指南针以方向为主弱化绝对坐标 |
| 高并发服务器成本 | 大型活动短时海量位置同步 | 自适应上报频率、消息合并、按小队分片、弹性扩容、空闲降频 |
| 隐私合规 | 位置数据敏感 | 短时效存储、最小化采集、明示同意、隐私政策、数据隔离（见 §9） |
| 后台被系统杀死 | iOS/Android 后台限制 | 合理使用后台定位能力、前台服务/通知；断线重连 |
| 电量消耗 | 持续定位耗电 | 自适应频率、静止降频、低电量提示 |

## 14. 盈利模式

> 来源于创意设想，作为商业化方向规划，非 MVP 必做功能。

- **基础功能免费**：建队、加入、实时位置、指南针指引。
- **高级功能付费**：
  - 更大小队人数上限
  - 历史轨迹回放
  - 自定义地图标记 / 兴趣点
  - （可扩展）更长共享时长、更高上报频率等

## 16. 验收标准

MVP 的整体验收以「场景 A 端到端跑通」为准：

1. **建队/加入**：队长创建小队生成二维码，成员扫码后 2 步内进入小队并出现在成员列表。
2. **实时位置**：双方开启共享后，地图上互相可见，位置更新延迟 ≤ 3 秒，且显示移动方向。
3. **指南针**：选中目标成员后，箭头随自身朝向旋转并指向对方，距离随移动实时变化，接近时有"即将会合"提示。
4. **隐私**：暂停共享后对方立即看不到实时位置；解散小队后位置数据被清除，无法再访问。
5. **后台**：应用切后台后仍能持续共享（在系统允许范围内）。
