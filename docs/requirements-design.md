## 2. 产品定位与目标

### 2.1 一句话定位

**一款让单台 Linux 服务器"整机搬家"变得简单、可靠、自动化的命令行工具。**

### 2.2 解决的核心痛点

个人开发者与小团队在迁移服务器时，需要手动记录并搬运软件清单、应用文件、数据库、定时任务、环境变量等，过程繁琐、极易遗漏，迁移后常出故障。

### 2.3 产品目标

| 目标 | 衡量方式 |
| --- | --- |
| 降低迁移门槛 | 用户通过 3 步（采集 → 传输 → 还原）即可完成迁移 |
| 减少遗漏 | 自动采集系统软件、文件、数据库、定时任务、环境变量五大类内容 |
| 提升可靠性 | 全程日志可追溯，还原冲突有明确提示 |
| 保障安全 | 敏感信息支持加密打包 |

### 2.4 非目标（当前版本不追求）

- 不追求"零差异克隆"（如内核版本、磁盘镜像级别的完全一致）
- 不做实时/持续同步（一次性迁移为主）
- 不做跨架构（如 x86 → ARM）的二进制自动转换

## 3. 术语与约定

| 术语 | 含义 |
| --- | --- |
| 源服务器（Source） | 需要被迁出的原服务器 |
| 目标服务器（Target） | 接收迁移内容的新服务器 |
| 采集（Collect / Pack） | 在源服务器上扫描并打包关键内容的过程 |
| 还原（Restore） | 在目标服务器上根据迁移包重建环境的过程 |
| 迁移包（Bundle） | 采集阶段产出的压缩归档文件 |
| 迁移清单（Manifest） | 描述迁移包内容的人类可读元数据文件 |
| 模块（Module） | 一类可独立采集/还原的内容，如「数据库模块」「定时任务模块」 |

## 4. 用户与场景

### 4.1 目标用户画像

- **个人开发者**：几个网站 / 小程序后端跑在云服务器上
- **小团队运维**：管理 1~10 台服务器
- **外包开发者**：经常需要给客户部署、交付整套环境

共同特征：技术能力中等、对成本敏感、希望迁移"省心"。

### 4.2 核心场景

**场景 A：换服务器（主场景）**
小王在 A 云厂商的服务器到期，要换到 B 云厂商。服务器上跑着 2 个 Node.js 网站、1 个 MySQL 数据库、Nginx 反向代理、几个 crontab 任务。期望在新服务器上以最少精力把这些原样跑起来。

**场景 B：环境复制**
团队想把生产环境完整复制为测试环境，要求软件版本、配置尽量一致。

**场景 C：灾难恢复备份**
定期采集生产服务器，将迁移包异地保存；故障时可在新机器上快速还原。

### 4.3 用户旅程（场景 A）

```
源服务器                          目标服务器
  │                                  │
  ├─ 1. 运行 collect（交互式引导）     │
  ├─ 2. 生成加密迁移包 bundle.tar.gz │
  │                                  │
  └──── 3. scp 传输 ───────────────▶ │
                                     ├─ 4. 运行 preflight 兼容性检查
                                     ├─ 5. 运行 restore（按清单还原）
                                     └─ 6. 查看报告 / 校验服务状态
```

## 5. 整体方案设计

### 5.1 架构分层

```
┌─────────────────────────────────────────────┐
│                  CLI 入口层                    │
│   collect / restore / preflight / inspect     │
├─────────────────────────────────────────────┤
│                  编排引擎层                     │
│   流程调度、交互引导、日志、错误处理、加密       │
├─────────────────────────────────────────────┤
│                  模块插件层                     │
│  packages │ files │ database │ services │ env  │
│   每个模块实现 collect() / restore() 接口      │
├─────────────────────────────────────────────┤
│                  适配器层                       │
│  包管理器(apt/yum) │ 数据库dump工具 │ systemd   │
└─────────────────────────────────────────────┘
```

### 5.2 模块化设计原则

- 每个内容类别独立为一个**模块**，遵循统一的 `collect()` / `restore()` 接口。
- 模块可被单独启用 / 禁用（如只迁移数据库）。
- 新增数据库类型、新增内容类别 = 新增一个模块，符合「可扩展性」要求。

### 5.3 五大采集模块概览

| 模块 | 采集内容 | 优先级 |
| --- | --- | --- |
| `packages` | 包管理器软件清单、手动安装软件、运行中服务 | M |
| `files` | 用户指定目录、`/etc` 关键配置 | M |
| `database` | MySQL / PostgreSQL / MongoDB dump | M |
| `services` | systemd 服务、开机自启 | M |
| `env` | 环境变量、crontab 定时任务 | M |

## 6. 功能需求详述

### 6.1 源服务器：信息采集与打包

#### 6.1.1 系统软件清单（模块 `packages`）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PKG-01 | 采集包管理器已安装软件列表（apt: `dpkg --get-selections`；yum/dnf: `rpm -qa`） | M |
| F-PKG-02 | 识别并记录运行中的 systemd 服务列表 | M |
| F-PKG-03 | 尽力识别手动安装软件（源码编译/二进制），至少记录 `/usr/local`、`/opt` 下可执行文件与版本线索 | S |
| F-PKG-04 | 记录包管理器类型与发行版信息，供还原端匹配 | M |

> 说明：手动安装软件难以 100% 自动还原，MVP 阶段以"记录 + 提示用户手动处理"为主。

#### 6.1.2 应用代码与文件（模块 `files`）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-FILE-01 | 支持用户在配置/交互中指定需迁移的目录（如 `/var/www`、`/opt/app`） | M |
| F-FILE-02 | 支持采集 `/etc` 下的关键配置文件（如 nginx、ssh 等，提供推荐清单） | M |
| F-FILE-03 | 支持 include / exclude 规则（glob），便于排除 `node_modules`、日志、缓存等 | S |
| F-FILE-04 | 保留文件权限、属主、符号链接、时间戳等元数据 | M |
| F-FILE-05 | 记录每个文件的校验和（如 sha256），用于还原后完整性校验 | S |

#### 6.1.3 数据库（模块 `database`）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-DB-01 | 支持 MySQL / MariaDB 导出（调用 `mysqldump`） | M |
| F-DB-02 | 支持 PostgreSQL 导出（调用 `pg_dump` / `pg_dumpall`） | M |
| F-DB-03 | 支持 MongoDB 导出（调用 `mongodump`） | S |
| F-DB-04 | 支持指定库 / 全量库导出，连接信息通过配置或交互输入 | M |
| F-DB-05 | 自动检测本机存在的数据库实例并提示用户 | S |
| F-DB-06 | 数据库凭据不明文落盘到清单，仅存于加密包内或运行时输入 | M |

#### 6.1.4 运行环境（模块 `env` + `services`）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-ENV-01 | 采集系统级与指定用户的环境变量（如 `/etc/environment`、`~/.profile` 等来源，需脱敏提示） | M |
| F-ENV-02 | 采集 crontab 定时任务（系统级 `/etc/crontab`、`/etc/cron.*`、各用户 crontab） | M |
| F-ENV-03 | 采集开机自启服务（systemd `enabled` 单元） | M |

### 6.2 打包产物（详见 [第 7 章](#7-迁移产物规范)）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PACK-01 | 将采集内容打包为一个或多个 `tar.gz` | M |
| F-PACK-02 | 生成人类可读的迁移清单（JSON 或 YAML） | M |
| F-PACK-03 | 大文件/大数据库支持分卷打包 | C |

### 6.3 目标服务器：还原

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-RST-01 | 读取并校验迁移包与清单（含完整性校验、解密） | M |
| F-RST-02 | 按清单依次还原：安装软件 → 恢复文件 → 导入数据库 → 恢复定时任务 / 服务 | M |
| F-RST-03 | 支持选择性还原（只还原指定模块） | S |
| F-RST-04 | 支持「演练模式」（dry-run），只输出将执行的操作而不实际改动 | S |
| F-RST-05 | 还原冲突（文件已存在、端口占用、版本不符等）需明确提示，并提供覆盖/跳过/中止选项 | M |
| F-RST-06 | 还原结束输出结果报告（成功/失败/跳过的条目） | M |

### 6.4 兼容性预检（`preflight`）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PRE-01 | 还原前检查目标机发行版/包管理器是否与源匹配 | S |
| F-PRE-02 | 检查磁盘空间、必要依赖（dump 还原工具）、端口占用等 | S |
| F-PRE-03 | 输出预检报告，存在阻断项时拒绝/警告 | S |

## 7. 迁移产物规范

### 7.1 迁移包目录结构（解包后）

```
bundle/
├── manifest.yaml            # 迁移清单（人类可读）
├── checksums.sha256         # 各产物文件校验和
├── packages/
│   ├── apt-selections.txt   # / rpm-list.txt
│   └── services.json
├── files/
│   └── var-www.tar.gz       # 按来源分卷的文件归档
│   └── etc-configs.tar.gz
├── database/
│   ├── mysql/<db>.sql.gz
│   └── postgres/<db>.dump
├── env/
│   ├── environment.txt
│   └── crontabs/<user>.cron
└── logs/
    └── collect.log
```

### 7.2 迁移清单（Manifest）示例

```yaml
schema_version: "1.0"
created_at: "2026-05-31T10:00:00Z"
source:
  hostname: web-01
  os: ubuntu
  os_version: "22.04"
  arch: x86_64
  package_manager: apt
encryption:
  enabled: true
  method: age            # 或 gpg / aes-256-gcm
modules:
  packages:
    enabled: true
    count: 412
    artifact: packages/apt-selections.txt
  files:
    enabled: true
    entries:
      - path: /var/www
        artifact: files/var-www.tar.gz
        bytes: 184320213
        sha256: "..."
  database:
    enabled: true
    engines:
      - type: mysql
        version: "8.0.36"
        databases: [app, sessions]
  env:
    enabled: true
    crontab_users: [root, www-data]
```

> 设计要点：清单**只描述结构与元数据**，**不存放明文密码/密钥**；敏感信息随加密产物一同保存。

## 8. 安全性设计

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| SEC-01 | 迁移包支持加密（推荐 `age` 或 GPG；或 AES-256-GCM 对称加密 + 口令） | M |
| SEC-02 | 数据库密码、密钥等敏感信息不以明文写入清单 | M |
| SEC-03 | 采集时对疑似敏感内容（私钥、`.env`、凭据文件）进行识别并提示用户 | S |
| SEC-04 | 不内置传输功能，引导用户使用 scp/sftp 等安全通道传输（文档化最佳实践） | M |
| SEC-05 | 临时解密文件使用受限权限目录，结束后安全清理 | S |
| SEC-06 | 加密口令不写入日志、不出现在进程参数明文中（通过 stdin / 环境变量 / 密钥文件传入） | M |

## 9. 非功能需求

| 类别 | 需求 |
| --- | --- |
| **易用性** | CLI 命令简单，提供交互式引导；关键步骤有清晰中文/英文提示与进度展示 |
| **可靠性** | 全流程日志（collect.log / restore.log），错误可定位；单模块失败不影响其余模块（可配置） |
| **可重入性** | 还原支持幂等/可重试，避免重复执行造成损坏 |
| **兼容性** | 优先支持 Ubuntu、Debian、CentOS；明确声明已测试版本矩阵 |
| **可扩展性** | 模块化插件架构，新增数据库/内容类别成本低 |
| **性能** | 大目录/大数据库打包采用流式压缩，避免占用过多临时空间；支持并行采集（可选） |
| **可移植性** | 工具自身尽量单文件分发，依赖最少 |

## 10. 技术选型建议

| 维度 | 建议 | 理由 |
| --- | --- | --- |
| 开发语言 | **Go**（首选）或 Python | Go 可静态编译为单文件、跨发行版分发无依赖；Python 生态熟悉但需处理运行时依赖 |
| 打包格式 | `tar.gz` + 清单文件 | 通用、可被标准工具解开，降低锁定风险 |
| 数据库导出 | 调用各数据库自带 dump 工具 | 兼容性最好，避免重复造轮子 |
| 加密 | `age`（现代、简单）或 GPG；对称场景用 AES-256-GCM | 满足 SEC-01 |
| 清单格式 | YAML（人类友好）或 JSON | 满足 F-PACK-02 |
| 日志 | 结构化日志 + 人类可读控制台输出 | 满足可靠性需求 |

## 11. 命令行接口（CLI）设计

### 11.1 命令总览

```bash
super-baby collect    [options]   # 源服务器：采集并打包
super-baby restore    [options]   # 目标服务器：还原
super-baby preflight  [options]   # 目标服务器：兼容性预检
super-baby inspect    <bundle>    # 查看迁移包清单内容（不还原）
```

### 11.2 `collect` 示例

```bash
# 交互式引导（推荐新手）
super-baby collect

# 非交互 / 配置文件驱动
super-baby collect \
  --config ./migrate.yaml \
  --output ./bundle.tar.gz \
  --encrypt --recipient age1xxxx \
  --modules packages,files,database,env
```

### 11.3 `restore` 示例

```bash
# 演练模式，先看会做什么
super-baby restore --bundle ./bundle.tar.gz --dry-run

# 实际还原，仅还原文件与数据库
super-baby restore --bundle ./bundle.tar.gz \
  --modules files,database \
  --on-conflict prompt          # prompt | overwrite | skip | abort
```

### 11.4 通用选项

| 选项 | 说明 |
| --- | --- |
| `--config <file>` | 指定配置文件 |
| `--modules <list>` | 仅处理指定模块 |
| `--log-file <path>` | 日志输出路径 |
| `--yes` | 跳过交互确认（自动化场景） |
| `--verbose` | 详细输出 |

### 11.5 配置文件示例（`migrate.yaml`）

```yaml
modules:
  files:
    include:
      - /var/www
      - /opt/app
    exclude:
      - "**/node_modules"
      - "**/*.log"
  database:
    mysql:
      host: 127.0.0.1
      user: root
      databases: [app, sessions]   # 留空表示全量
  env:
    crontab: true
encryption:
  enabled: true
  method: age
```

## 12. 迁移流程时序

### 12.1 采集（collect）

```
用户 → CLI: super-baby collect
CLI → 引擎: 加载配置/交互收集参数
引擎 → 各模块: collect()
  packages → 适配器: 读取包列表/服务
  files    → 适配器: 流式 tar 打包目录
  database → 适配器: 调用 dump 工具
  env      → 适配器: 读取 crontab/环境变量
引擎: 生成 manifest + checksums
引擎: (可选) 加密 → 产出 bundle.tar.gz
CLI → 用户: 输出结果与下一步指引（如何传输）
```

### 12.2 还原（restore）

```
用户 → CLI: super-baby restore --bundle ...
CLI → 引擎: 解密 + 校验完整性 + 解析 manifest
引擎 → preflight: 检查发行版/空间/依赖（可选）
引擎 → 各模块: restore()（按依赖顺序）
  packages → 安装软件
  files    → 恢复文件（处理冲突）
  database → 创建库 + 导入 dump
  env      → 恢复 crontab/自启服务
引擎: 汇总结果报告
CLI → 用户: 输出成功/失败/跳过明细
```

> 还原顺序约定：**软件包 → 文件 → 数据库 → 服务/定时任务**，确保依赖先于使用者就位。

## 13. 边界、风险与限制

| 风险/限制 | 说明 | 缓解措施 |
| --- | --- | --- |
| 手动安装软件难以自动还原 | 源码编译/二进制安装无标准元数据 | 仅记录并提示用户手动处理（F-PKG-03） |
| 跨发行版/跨架构差异 | 包名、版本、ABI 可能不一致 | preflight 预检 + 明确兼容矩阵；跨架构列为 W |
| 数据库版本不一致 | dump 在高/低版本间可能不完全兼容 | 清单记录版本并预检告警 |
| 运行中数据库一致性 | 在线 dump 可能存在事务一致性问题 | 推荐使用一致性快照参数（如 `--single-transaction`） |
| 大数据量迁移耗时/占空间 | 大文件、大库 | 流式压缩、分卷、提示预留空间 |
| 敏感信息泄露 | 包内含密码/密钥 | 默认建议加密（第 8 章） |

## 16. 验收标准

MVP 的整体验收以「场景 A 端到端跑通」为准：

1. **采集**：在一台装有 Node.js 应用、MySQL、Nginx、crontab 的源服务器上运行 `collect`，成功产出加密迁移包与可读清单，全程无致命错误且有日志。
2. **传输**：迁移包可通过 scp 正常传输到目标机。
3. **还原**：在同发行版目标机运行 `restore`，软件包安装、`/var/www` 与 nginx 配置恢复、MySQL 数据导入、crontab 恢复全部成功；冲突有明确提示。
4. **可用性**：还原后 Nginx 与 Node.js 应用可启动，数据库数据完整（行数/校验比对一致）。
5. **安全**：迁移包为加密态，清单中不含明文数据库密码。
6. **可观测**：collect/restore 均产出可追溯日志与结果报告。

| 模块级验收要点 | 通过标准 |
| --- | --- |
| packages | 软件清单可被还原端用于批量安装，数量与源一致 |
| files | 文件内容、权限、属主一致，校验和匹配 |
| database | 导出可成功导入，关键表行数一致 |
| env / services | crontab 条目、自启服务在目标机生效 |
| 加密 | 错误口令无法解包；正确口令可还原 |
