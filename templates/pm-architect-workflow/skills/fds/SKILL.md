# 流程二：生成《功能设计文档》

你（主控/orchestrator）按本剧本编排 **architect**（主笔）与 **developer**（评审）。
两个 agent 上下文相互隔离、也看不到主线程，**唯一可靠的事实来源是落盘的文档文件**。

输入需求文档：`$ARGUMENTS`（若为空，先在 `docs/requirements/` 下确认用哪一份，必要时问用户）。功能设计文档默认与对应需求文档同目录。

## 铁律（贯穿全程）

1. **文件即事实来源**：功能设计文档默认存到 `docs/requirements/<feature>/<feature>-fds.md`（与对应需求文档 `<feature>-prd.md` 同目录；除非用户另行指定路径）。每次调用 agent，prompt 必须给出：① 需求文档路径；② 功能设计文档路径（要求先 Read 最新版）；③ 对方上一轮的**完整**意见原文。developer 评审时**必须同时拿到需求文档路径**。
2. **问题不许丢**：每轮返回后扫出标注问题并路由——
   - 【设计疑问·待架构师确认】→ 转 architect 逐条答复。
   - 【需求澄清·待 PM 确认】→ 这是设计阶段触及的需求歧义；暂停并提示用户「可能需要回流程一澄清需求」，或在用户同意下记为待办。
   - 【业务澄清·待用户决策】→ 暂停问用户。
   - 不允许任何问题无人回应。
3. **每轮向用户播报**：当前进展、是否达成一致、待用户决策的事项。

## 撰写要求（FDS 内容与组织规约）

architect 主笔/修订 FDS 时除铁律外必须满足以下要求；developer 评审时一并据此核对，缺失或违规即视为"必须改"。

### 一、组织原则：按功能点组织，不按图的类型组织

FDS 必须**以功能点/子系统/分层为主线组织**（如"感知层""任务层 FSM""视觉伺服""认知层"等），**每个功能点把它的图与说明聚在一起、自成一节**，围绕三个问题展开：

- **有哪些类**（类图）——该功能点的核心对象与关系；
- **主流程怎么设计**（状态图）——该功能点的关键状态机/主流程（**有状态机/主流程的功能点必带；纯数据、无状态的功能点可省**）；
- **具体怎么实现**（序列图）——该功能点关键流程的对象交互时序。

**禁止按图的类型集中堆放**（例如"把全文所有类图放一节、所有状态图放另一节、所有序列图放第三节"）。读者应能在某一功能点的小节里同时看到它的类图/状态图/序列图与文字说明，而不必跳转全文拼凑。

### 二、必备图示（全局一张模块图 + 每功能点自带图）

1. **全局必带一张模块图**：置于架构概览处，交代本次设计涉及的各模块及模块间依赖（跨功能点的整体结构与边界）。缺失即"必须改"。
2. **每个核心功能点必带类图**；**有状态机/主流程的功能点必带状态图**；**关键功能点/主流程必带序列图**。整篇 FDS 至少应出现类图、状态图、序列图各一（分散在相应功能点小节内）；某一类图示完全缺失须说明理由，否则视为"必须改"。

### 三、画法规约

3. **模块图——内容与画法**：标出本次设计涉及的各模块（新增/改动的为主，必要时带上相邻的既有模块以交代边界），并用带箭头的边表示模块间**依赖关系**（箭头由依赖方指向被依赖方）。目的是交代整体结构与边界，模块粒度即可，不要下钻到类或函数。
4. **类图——继承关系画法**：统一从派生（子）类的**顶边**拉出一条线**向上**，箭头到达被继承（父）类的**底边**——即父类在上、子类在下，继承箭头朝上指向父类。类图目的是揭示层级结构与核心对象关系，一定不要列举所有 fields/methods。
5. **类图——依赖关系画法**：从依赖方类的**右边**拉出一条线，箭头到达被依赖类的**左边**——即依赖方在左、被依赖方在右，依赖箭头朝右指向被依赖类。
6. **序列图——画法**：participant 沿用既有模块/对象命名，消息忠实反映调用/读写方向与时序，必要时以 note 标注周期/线程；目的是呈现该功能点"具体怎么实现"的对象交互。

> 落地提示（Mermaid）：模块图用 `flowchart LR`，模块为节点、依赖用 `A --> B`（A 依赖 B）。类图用 `classDiagram`：继承写 `父类 <|-- 子类`（默认 `direction TB` 即把父类排上方、三角箭头落在父类底部）；依赖写 `依赖类 ..> 被依赖类`，并借 `direction`/声明顺序把被依赖类摆到右侧。状态图用 `stateDiagram-v2`，序列图用 `sequenceDiagram`。Mermaid 自动布局只能尽量逼近上述"边位"约定、不保证像素级锚点，类图达标判据为「父在上/子在下、依赖在左/被依赖在右、箭头方向正确」。

## 编排步骤

**Step 1 — architect 撰写初稿**
调用 `architect`：给需求文档路径（要求先 Read）+ 目标设计文档路径，要求**以架构设计开头**、文字+图表为主少用伪代码、聚焦变化点、给出"需求→设计映射"、并遵守上文《撰写要求》（**按功能点组织**、每个功能点聚合其类图/状态图/序列图；全局一张模块图；画法按规约），落盘。

**Step 2 — developer 评审**
调用 `developer`：给设计文档路径 + **需求文档路径**（均要求先 Read 最新版），要求：
(a) 开头先给"需求/user story 覆盖度小结"（逐条核对，标出已覆盖/缺失/存疑）；
(b) 从代码实现角度产出评审意见清单；
(c) 核对《撰写要求》：① 是否**按功能点组织**（而非按图类型集中堆放）、每个核心功能点是否聚合其类图/（有状态机则）状态图/序列图；② 全局模块图是否齐备；③ 模块图依赖、类图继承/依赖、序列图画法是否符合规约；缺失或违规标为"必须改"。

**Step 3 — architect 逐条回应并修订**
调用 `architect`：给设计文档路径 + developer 的**完整评审意见**原文（含覆盖度小结），要求逐条回应（采纳/部分采纳/不采纳+理由）并更新落盘文档。

**Step 4 — 往返收敛**
重复 Step 2–3，直至 developer 无"必须改"意见、且覆盖度小结显示需求全覆盖。一般 ≤2~3 轮。新问题继续按铁律2路由。

**Step 5 — 终轮整体复审（解决"局部改完没人看全局"）**
developer 声明逐条意见已解决后，**额外再调用一次 developer**，明确要求：**抛开局部 diff，重新通读全文**，复核 ① 需求/user story 是否仍全覆盖、② 局部修改是否引入全局不一致/矛盾。
- 若发现新问题 → 回到 Step 3，然后再做一次本步骤。
- 若确认整体无问题 → 进入 Step 6。

**Step 6 — 交用户决策**
向用户汇报：最终设计文档路径 + 摘要 + 需求覆盖度结论 + 双方达成一致的说明 + 任何遗留权衡点 + 终轮整体复审结论。明确这是**设计决策**节点，由用户拍板。不替用户决策。

> 提示：如已启用 agent teams，可用 SendMessage 续同一 agent 实例保留推理；非必需，跨会话失效——以文档文件为准。
