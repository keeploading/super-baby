# 流程二：生成《功能设计文档》

你（主控/orchestrator）按本剧本编排 **architect**（主笔）与 **developer**（评审）。
两个 agent 上下文相互隔离、也看不到主线程，**唯一可靠的事实来源是落盘的文档文件**。

输入需求文档：`$ARGUMENTS`（若为空，先在 `docs/requirements/` 下确认用哪一份，必要时问用户）。

## 铁律（贯穿全程）

1. **文件即事实来源**：功能设计文档固定存到 `docs/design/<主题>-功能设计.md`。每次调用 agent，prompt 必须给出：① 需求文档路径；② 功能设计文档路径（要求先 Read 最新版）；③ 对方上一轮的**完整**意见原文。developer 评审时**必须同时拿到需求文档路径**。
2. **问题不许丢**：每轮返回后扫出标注问题并路由——
   - 【设计疑问·待架构师确认】→ 转 architect 逐条答复。
   - 【需求澄清·待 PM 确认】→ 这是设计阶段触及的需求歧义；暂停并提示用户「可能需要回流程一澄清需求」，或在用户同意下记为待办。
   - 【业务澄清·待用户决策】→ 暂停问用户。
   - 不允许任何问题无人回应。
3. **每轮向用户播报**：当前进展、是否达成一致、待用户决策的事项。

## 编排步骤

**Step 1 — architect 撰写初稿**
调用 `architect`：给需求文档路径（要求先 Read）+ 目标设计文档路径，要求**以架构设计开头**、文字+图表为主少用伪代码、聚焦变化点、并给出"需求→设计映射"，落盘。

**Step 2 — developer 评审**
调用 `developer`：给设计文档路径 + **需求文档路径**（均要求先 Read 最新版），要求：
(a) 开头先给"需求/user story 覆盖度小结"（逐条核对，标出已覆盖/缺失/存疑）；
(b) 从代码实现角度产出评审意见清单。

**Step 3 — architect 逐条回应并修订**
调用 `architect`：给设计文档路径 + developer 的**完整评审意见**原文（含覆盖度小结），要求逐条回应（采纳/部分采纳/不采纳+理由）并更新落盘文档。

**Step 4 — 往返收敛**
重复 Step 2–3，直至 developer 无"必须改"意见、且覆盖度小结显示需求全覆盖。一般 ≤2~3 轮。新问题继续按铁律2路由。

**Step 5 — 终轮整体复审（解决"局部改完没人看全局"）**
developer 声明逐条意见已解决后，**额外再调用一次 developer**，明确要求：**抛开局部 diff，重新通读全文**，复核 ① 需求/user story 是否仍全覆盖、② 局部修改是否引入全局不一致/矛盾。
- 若发现新问题 → 回到 Step 3，然后再做一次本步骤。
- 若确认整体无问题 → 进入 Step 6。

**Step 6 — 交用户决策**
向用户汇报：最终设计文档路径 + 摘要 + 需求覆盖度结论 + 双方达成一致的说明 + 任何遗留权衡点 + 终轮整体复审结论。明确这是**设计决策**节点，由用户拍板。不替用户决策。

> 提示：如已启用 agent teams，可用 SendMessage 续同一 agent 实例保留推理；非必需，跨会话失效——以文档文件为准。
