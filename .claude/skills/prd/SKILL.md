# 流程一：生成《需求设计文档》

你（主控/orchestrator）按本剧本编排 **product-manager**（主笔）与 **architect**（评审）。
两个 agent 上下文相互隔离、也看不到主线程，**唯一可靠的事实来源是落盘的文档文件**。因此每次调用 agent，你都必须把它需要的上下文显式喂进去。

用户的原始诉求：`$ARGUMENTS`（若为空，先向用户问清要做什么再开始）。

## 铁律（贯穿全程）

1. **文件即事实来源**：需求文档默认存到 `docs/requirements/<feature>/<feature>-prd.md`（`<feature>` 为该需求的简短英文/拼音标识；除非用户另行指定路径）。每次调用 agent，prompt 里必须给出：① 用户原始诉求；② 该文档的绝对路径（并要求 agent 先 Read 最新版）；③ 对方上一轮的**完整**意见原文（不要自己缩写）。
2. **问题不许丢**（解决"PM 抛问题没人理"）：每轮 agent 返回后，你必须扫出其中标注的问题并分类路由——
   - 【技术疑问·待架构师确认】→ 下一轮转给 architect 要求逐条答复。
   - 【业务澄清·待用户决策】→ 暂停，汇总后问用户，拿到答复再继续。
   - 不允许任何问题无人回应。
3. **每轮向用户播报**：当前进展、是否达成一致、待用户确认/决策的事项。

## 编排步骤

**Step 1 — PM 撰写初稿**
调用 `product-manager`：给原始诉求 + 目标文件路径，要求以 user story 视角撰写并落盘。
收回后：记录它抛出的【业务澄清】与【技术疑问】。若有【业务澄清】，先问用户（见铁律2）。

**Step 2 — architect 评审**
调用 `architect`：给文件路径（要求先 Read 最新版）+ 原始诉求 + PM 抛出的【技术疑问】原文，要求：
(a) 产出评审意见清单；(b) **逐条答复 PM 的技术疑问**。

**Step 3 — PM 逐条回应并修订**
调用 `product-manager`：给文件路径 + architect 的**完整评审意见 + 技术疑问答复**原文，要求逐条回应（采纳/部分采纳/不采纳+理由）并更新落盘文档。

**Step 4 — 往返收敛**
重复 Step 2–3，直至 architect 无"必须改"意见。一般 ≤2~3 轮。其间产生的新问题继续按铁律2路由。

**Step 5 — 终轮整体复审（解决"局部改完没人看全局"）**
architect 声明逐条意见已解决后，**额外再调用一次 architect**，明确要求：**抛开局部 diff，重新通读全文**，检查局部修改是否引入了全局不一致/矛盾/遗漏。
- 若发现新问题 → 回到 Step 3 修订，然后再做一次本步骤。
- 若确认整体无问题 → 进入 Step 6。

**Step 6 — 交用户确认**
向用户汇报：最终文档路径 + 摘要 + 双方意见与遗留权衡点 + 终轮整体复审结论。明确这是**需求确认**节点，由用户拍板。不替用户决策。

> 提示：如已启用 agent teams，可用 SendMessage 续同一 agent 实例以保留其推理；但这非必需，且跨会话失效——任何情况下都以文档文件为准。
