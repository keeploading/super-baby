# 流程二：生成《功能设计文档》

你（主控/orchestrator）按本剧本编排 **architect**（主笔）与 **developer**（评审）。
两个 agent 上下文相互隔离、也看不到主线程，**唯一可靠的事实来源是落盘的文档文件**。

输入需求文档：`$ARGUMENTS`（若为空，先在 `docs/requirements/` 下确认用哪一份，必要时问用户）。功能设计文档默认与对应需求文档同目录。

## 铁律（贯穿全程）

1. **文件即事实来源**：功能设计文档默认存到 `docs/requirements/<feature>/<feature>-fds.md`（与对应需求文档 `<feature>-prd.md` 同目录；除非用户另行指定路径）。每次调用 agent，prompt 必须给出：① 需求文档路径；② 功能设计文档路径（要求先 Read 最新版）；③ 对方上一轮的**完整**意见原文。developer 评审时**必须同时拿到需求文档路径**。
2. **问题不许丢**：每轮返回后扫出标注问题并路由——
   - 【设计疑问·待架构师确认】→ 转 architect 逐条答复。
   - 【需求澄清·待 PM 确认】→ 这是设计阶段触及的需求歧义；暂停并提示用户「可能需要回流程一澄清需求」，或在用户同意下记为待办。
   - 【业务澄清·待用户决策】→ 暂停问用户。
   - 不允许任何问题无人回应。
3. **每轮向用户播报**：当前进展、是否达成一致、待用户决策的事项。

## 撰写要求（FDS 内容与图示规约）

architect 主笔/修订 FDS 时除铁律外必须满足以下要求；developer 评审时一并据此核对，缺失或违规即视为"必须改"。

1. **必带类图与状态图**：FDS 必须至少包含一张**类图**（分层或核心对象的类与关系）与一张**状态图**（主流程/关键状态机）。二者缺一即为"必须改"。
2. **类图——继承关系画法**：统一从派生（子）类的**顶边**拉出一条线**向上**，箭头到达被继承（父）类的**底边**——即父类在上、子类在下，继承箭头朝上指向父类。
3. **类图——依赖关系画法**：从依赖方类的**右边**拉出一条线，箭头到达被依赖类的**左边**——即依赖方在左、被依赖方在右，依赖箭头朝右指向被依赖类。

> 落地提示（Mermaid `classDiagram`）：继承写 `父类 <|-- 子类`（默认 `direction TB` 即把父类排上方、三角箭头落在父类底部）；依赖写 `依赖类 ..> 被依赖类`，并借 `direction`/声明顺序把被依赖类摆到右侧。Mermaid 自动布局只能尽量逼近上述"边位"约定、不保证像素级锚点，达标判据为「父在上/子在下、依赖在左/被依赖在右、箭头方向正确」。

## 编排步骤

**Step 1 — architect 撰写初稿**
调用 `architect`：给需求文档路径（要求先 Read）+ 目标设计文档路径，要求**以架构设计开头**、文字+图表为主少用伪代码、聚焦变化点、给出"需求→设计映射"、并遵守上文《撰写要求》（必带类图与状态图，类图继承/依赖画法按规约），落盘。

**Step 2 — developer 评审**
调用 `developer`：给设计文档路径 + **需求文档路径**（均要求先 Read 最新版），要求：
(a) 开头先给"需求/user story 覆盖度小结"（逐条核对，标出已覆盖/缺失/存疑）；
(b) 从代码实现角度产出评审意见清单；
(c) 核对《撰写要求》：类图与状态图是否齐备、类图继承/依赖画法是否符合规约，缺失或违规标为"必须改"。

**Step 3 — architect 逐条回应并修订**
调用 `architect`：给设计文档路径 + developer 的**完整评审意见**原文（含覆盖度小结），要求逐条回应（采纳/部分采纳/不采纳+理由）并更新落盘文档。

**Step 4 — 往返收敛**
重复 Step 2–3，直至 developer 无"必须改"意见、且覆盖度小结显示需求全覆盖。一般 ≤2~3 轮。新问题继续按铁律2路由。

**Step 5 — 终轮整体复审（解决"局部改完没人看全局"）**
developer 声明逐条意见已解决后，**额外再调用一次 developer**，明确要求：**抛开局部 diff，重新通读全文**，复核 ① 需求/user story 是否仍全覆盖、② 局部修改是否引入全局不一致/矛盾。
- 若发现新问题 → 回到 Step 3，然后再做一次本步骤。
- 若确认整体无问题 → 进入 Step 6。

**Step 6 — 交用户决策**
向用户汇报：最终设计文档路径 + 摘要 + 需求覆盖度结论 + 双方达成一致的说明 + 任何遗留权衡点 + 终轮整体复审结论。明确这是**设计决策**节点，由用户拍板。不替用户决策。

> 提示：如已启用 agent teams，可用 SendMessage 续同一 agent 实例保留推理；非必需，跨会话失效——以文档文件为准。
